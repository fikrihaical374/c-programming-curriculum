0.4.1 — Installing the compiler and toolchain on Windows
Knowledge-unit ID: C23-P00-CH04-S01
Importance: Critical
Memory layers: Atomic, Conceptual, Procedural, Relationship, Engineering Judgment

1. Core idea
On Windows, C programs can be built with native toolchains such as MSVC or GCC/MinGW-w64 via MSYS2; an editor is just a place to write code and is not a replacement for a compiler, linker, or SDK.

2. Mental model
Think of the toolchain as a workshop: the compiler processes source, the assembler produces object files, the linker combines object files and libraries, while the runtime/OS provides services when the program runs. The editor is a drafting table. A good drafting table does not make the workshop available.

This analogy simplifies the process: modern compiler drivers can run several stages automatically, and stage details differ by toolchain and target.

3. Technical mechanism
Option A — MSYS2 UCRT64 + GCC (recommended path for cross-platform exercises).

Download the installer from the official MSYS2 site: https://www.msys2.org/.
Complete the installation using the default location unless you have an operational reason to change it.
Open the MSYS2 UCRT64 terminal from the Start Menu. Do not mix MSYS, MINGW64, UCRT64, and CLANG64 terminals without understanding their runtime and PATH differences.
Update packages according to MSYS2 instructions. If the update asks you to close the terminal, close it and relaunch the UCRT64 terminal, then finish the update.
Install GCC:
pacman -S mingw-w64-ucrt-x86_64-gcc
Verify:
gcc --version
gcc -dumpmachine
where gcc
MSYS2 documents UCRT64 as the recommended starting choice for users who are unsure. The UCRT64 GCC package is available in the MSYS2 repository. Package names and version availability may change; use the official package catalog when these instructions become outdated.

Option B — Microsoft Visual Studio Build Tools / Visual Studio + MSVC.

Download Visual Studio or Build Tools from https://visualstudio.microsoft.com/downloads/.
In the Visual Studio Installer, select the Desktop development with C++ workload. Ensure the appropriate MSVC toolset and Windows SDK components are selected.
Open the Developer Command Prompt or Developer PowerShell provided by the Visual Studio installation.
Check the compiler:
cl
MSVC is commonly invoked as cl.exe; that command depends on the environment set up by the Developer Command Prompt/PowerShell. If cl is not recognized in a regular terminal, it does not prove the installation is broken: that terminal may not have loaded the MSVC environment.

First verification program

Save as hello.c:

#include <stdio.h>
int main(void)
{
    puts("C toolchain ready.");
    return 0;
}
MSYS2 UCRT64:

gcc -std=c17 -Wall -Wextra -Wpedantic -Werror hello.c -o hello.exe
./hello.exe
MSVC Developer Command Prompt:

cl /nologo /W4 /WX /std:c17 hello.c /Fe:hello.exe
hello.exe
Expected output:

C toolchain ready.
This program intentionally uses basic features available long before C23. Success proves that the basic compile-link-run path works, not that all C23 features are supported.

4. Formal boundary
ISO C defines the C language and library, not Windows installer click procedures, MSYS2 terminal names, or Windows SDK choices.
MSVC, GCC, and Clang are different implementations. Command-line options, diagnostics, ABI, libraries, and feature support are not identical.
MSYS2 provides several environments. UCRT64 and MINGW64 must not be considered identical: they use different C runtime choices. Current MSYS2 documentation recommends UCRT64 for unsure users and announces deprecation of MINGW64; check the latest announcements before migrating old projects.
-std=c17 and /std:c17 select C17 mode on toolchains that support it. Do not equate a language mode option with proof of full conformance.
5. Practical consequence
On Windows, decide one primary toolchain for the exercises. Verify it can compile, link, and run a minimal program.
If you use both GCC and MSVC, keep their environments separate and record which terminal is used for each build.
Always record compiler version, target, and flags for reproducibility.
Pitfall — An editor is not a compiler. Installing VS Code and the C/C++ extension does not install GCC/Clang. A successful syntax highlight does not prove the toolchain is installed.

6. Retrieval question
Without looking, explain why an editor is not a substitute for a toolchain, and why UCRT64 and MINGW64 are not interchangeable.

0.4.2 — Installing the compiler and toolchain on Linux
Knowledge-unit ID: C23-P00-CH04-S02
Importance: Critical
Memory layers: Atomic, Conceptual, Procedural, Relationship

1. Core idea
On Linux, GCC is commonly available via the distro package manager, while Clang/LLVM is an alternative implementation with its own driver, target, and library integration.

2. Mental model
The package manager provides the workshop tools. Installing gcc gives you a compiler driver, but the assembler, linker, headers, and runtime come from the distro's toolchain layout.

3. Technical mechanism
Ubuntu/Debian example:

sudo apt update
sudo apt install build-essential
gcc --version
clang --version
Verification:

#include <stdio.h>
int main(void){ puts("Linux toolchain ready."); return 0; }
gcc -std=c17 -Wall -Wextra -Wpedantic -Werror hello.c -o hello
./hello
4. Formal boundary
ISO C does not define apt, build-essential, or distro package names.
Package versions determine available features; do not assume upstream latest.
cc may be a symlink to gcc or clang depending on the distro.
5. Practical consequence
Record distro version, compiler version, and target triple.
Test both GCC and Clang when portability matters.

0.4.4 — Using a C toolchain on Android (Termux) and distinguishing the NDK
Knowledge-unit ID: C23-P00-CH04-S04
Importance: Core

1. Core idea
Termux provides a Linux-like environment on Android with Clang, while the Android NDK is a cross-toolchain for building libraries/executables for Android ABIs.

2. Mental model
Termux Clang builds for Termux's own environment. NDK Clang builds for Android apps. They share LLVM upstream but have different targets, sysroots, and packaging rules.

3. Technical mechanism
Termux setup:

pkg update
pkg install clang
clang --version
clang -dumpmachine
command -v clang
Build C program

Save hello.c in Termux working directory:

clang -std=c17 -Wall -Wextra -Wpedantic -Werror hello.c -o hello
./hello
Understand Android NDK boundary

Use the Android NDK when the target is a library or executable to be built for an Android ABI and integrated into an Android app. The NDK has its own cross Clang toolchain, target triple, sysroot, API level, and packaging rules. Do not assume a Termux compiler that successfully builds a Termux executable automatically produces the correct artifact for an APK/AAB.

4. Formal boundary
ISO C does not define Termux, Android package manager, Android app sandbox, NDK, JNI, APK, or Android ABI.
Termux Clang and Android NDK Clang may share upstream LLVM, but their targets, sysroots, runtimes, configurations, and build purposes differ.
clang -dumpmachine helps identify the compiler's default target, but does not replace checking the target, sysroot, API level, and ABI required by the application.
Successfully running a binary inside Termux only proves that binary runs in the Termux environment tested; it does not prove the binary can be loaded by another Android app.
Package availability depends on Termux repository, device architecture, app version, and mirror status. If pkg update fails, read the repository/mirror message; do not immediately download random binaries.
C23 feature support status must be verified against the actual Termux Clang version. Do not infer full C23 support from the package name clang.
5. Practical consequence
For learning C basics from a phone, Termux + Clang is a practical path.
For building .so for Android apps, use the NDK according to project configuration and target ABI, not just changing the output extension from a Termux binary.
Record Termux version, Clang version, target triple, and command line when reporting issues.
Store projects in appropriate directories; shared storage access requires Termux permission and configuration. Do not assume every Android directory is writable.
Avoid running installation scripts you do not understand with broad access.
Pitfall box

"Successful compilation in Termux" is not the same as "library ready to be loaded by an Android app." Termux programs are built for its own environment and target. An NDK build must specify Android ABI, API level, sysroot, and appropriate dependencies.

6. Retrieval question
Why must Termux Clang not be automatically used as a replacement for the Android NDK to produce app .so? Name at least three things that must be checked in an NDK build.

Retrieval item ID: C23-P00-CH04-S04-RET-01

0.4.5 — IDEs, text editors, syntax highlighting, and project configuration
Knowledge-unit ID: C23-P00-CH04-S05
Importance: Core
Memory layers: Atomic, Conceptual, Procedural, Relationship, Engineering Judgment

1. Core idea
An editor or IDE helps write, navigate, and inspect code, but the build process still depends on the compiler, linker, project configuration, and dependencies actually used.

2. Mental model
The editor is the workbench; the language server/IntelliSense is an assistant that reads configuration and gives suggestions; the build system is the production instruction list; the compiler and linker are the tools that produce the program. Editor suggestions are not build results and are not the final authority on program semantics.

3. Technical mechanism
Tool choices

Text editor: lightweight, flexible, usually requires separate compiler and build configuration.
IDE: integrates editor, project model, build, debugger, and sometimes compiler/toolchain.
Syntax highlighting: token coloring based on editor rules. This is primarily a visual feature; color is not proof of valid code.
Completion/IntelliSense: analyzes code based on compiler path, include path, macros, standard mode, and project configuration. Wrong configuration can produce false errors or hide diagnostics.
Build system: stores rules for how source files, headers, libraries, and flags are transformed into targets. For small projects, direct compiler commands are enough; for large projects, use an appropriate build system.
VS Code configuration example

Install VS Code from https://code.visualstudio.com/ and the C/C++ extension from Microsoft. That extension provides editor/debugging integration features, but does not include a C compiler. Install a compiler separately per OS.

In the project folder, IntelliSense configuration must point to the same compiler used for the build. Illustrative example .vscode/c_cpp_properties.json for GCC Linux:

{
  "configurations": [
    {
      "name": "Linux-GCC",
      "includePath": ["${workspaceFolder}/**"],
      "defines": [],
      "compilerPath": "/usr/bin/gcc",
      "cStandard": "c17",
      "intelliSenseMode": "linux-gcc-x64"
    }
  ],
  "version": 4
}
Paths and modes above are only examples. Replace with actual compiler path and architecture. For projects with a build system, compile_commands.json or a configuration provider can give more accurate compile info than manually copying include paths.

Healthy minimum project configuration

Source is in a clear folder (src/).
Public headers are in a clear folder (include/).
Build output is separated from source (e.g. build/).
Compiler and standard mode are explicit.
Build command can be run from terminal, not just IDE button.
External dependencies and toolchain versions are recorded.
Debug configuration points to the correct build executable.
4. Formal boundary
ISO C does not require an IDE, syntax highlighting, IntelliSense, editor extensions, or a specific folder structure.
An editor may give diagnostics based on a parser/configuration different from the actual compiler. The build result with the target compiler is the relevant check for that build configuration.
cStandard in editor configuration sets the language model for editor analysis; it does not always change flags in the build command.
Editor include path and compiler include path are two configurations that can become out of sync.
IDE extensions can add features, but do not automatically install compilers or SDKs. Check the extension's official prerequisites.
IDE configuration files are project metadata, not part of the C language.
5. Practical consequence
Keep editor configuration in sync with build configuration.
Verify that IntelliSense compiler path matches build compiler path.
For teams, document how to set up the editor.
Pitfall box

IntelliSense green does not mean build green. Editor analysis uses its own configuration; the compiler build is the source of truth.

6. Retrieval question
Why can IntelliSense show no errors while the compiler build fails? What two configurations must be in sync?

Candidate misconception ID: MIS-P00-CH04-S05-01

0.4.6 — Terminal, shell, current working directory, and paths
Knowledge-unit ID: C23-P00-CH04-S06
Importance: Critical
Memory layers: Atomic, Conceptual, Procedural, Relationship, Engineering Judgment

1. Core idea
The terminal runs commands in the context of a specific shell and working directory; understanding current working directory, path, and command status prevents errors that look like compiler problems.

2. Mental model
Path is an address, current working directory (CWD) is the relative reference point, and shell is the command interpreter. hello.c is a relative address to CWD; /home/ana/project/hello.c is an absolute address on POSIX systems. Changing CWD can change the meaning of relative paths without changing the file itself.

3. Technical mechanism
Basic cross-shell commands

Purpose	POSIX shell (Linux/macOS/Termux)	PowerShell	CMD
Show directory	pwd	Get-Location	cd
List contents	ls -la	Get-ChildItem	dir
Change directory	cd src	Set-Location src / cd src	cd src
Create directory	mkdir build	New-Item -ItemType Directory build	mkdir build
Copy file	cp a.c b.c	Copy-Item a.c b.c	copy a.c b.c
Move/rename	mv a.c src/	Move-Item a.c src/	move a.c src\
Delete file	rm a.c	Remove-Item a.c	del a.c
Show contents	cat a.c	Get-Content a.c	type a.c
Commands and PowerShell aliases may differ from POSIX even when names look similar. Do not run mass deletion commands before checking CWD and target.

Safe work sequence

pwd
ls -la
mkdir -p c-lab
cd c-lab
pwd
Create hello.c, then:

cc -std=c17 -Wall -Wextra -Wpedantic -Werror hello.c -o hello
./hello
cc is a common compiler driver name on Unix-like systems, but the actual executable depends on the system. If cc is unavailable, use a verified compiler, e.g. gcc or clang.

Important paths

Absolute: starts from root/drive or OS absolute form, e.g. /home/ana/project or C:\Users\Ana\project.
Relative: calculated from CWD, e.g. src/main.c.
. means current directory.
.. means parent directory.
Windows paths often use \; many tools also accept /, but do not assume every app handles all forms identically.
Spaces in path names need quoting per shell: cd "My Projects".
Command status

On POSIX shell, the last command's exit code can be checked with:

echo $?
Code 0 commonly means success; nonzero indicates failure per program convention. This is a process interface convention, not a C language rule. In PowerShell, check $LASTEXITCODE for native program exit code; $? is the last PowerShell command success status and is not identical in all contexts.

4. Formal boundary
ISO C does not define shell, process CWD, OS path separators, cd command, or shell exit status.
The C standard library has concepts of current locale and file streams, but that is not a shell filesystem command spec.
Absolute/relative paths, case sensitivity, file permissions, symlinks, drive letters, and separators differ across OS/filesystems.
./program is a common invocation method on POSIX shells; PowerShell and Windows command shells have different executable search rules.
Exit code 0 does not prove program logic is correct; it is only the status reported by the process. A program can produce wrong output and still exit with status 0.
5. Practical consequence
BeforBefore compiling, do three checks: (1) CWD, (2) source file existence, (3) which compiler is invoked. If output is not found, check output location and build exit status. If include is not found, check include path and header location.

**Pitfall box**

> **`gcc hello.c -o build/hello` failing is not always because code is wrong.** If `build/` folder does not exist, the linker cannot create output in that path. Create the folder first or point output to an existing location.

## 0.4.7 — Managing .c source files and .h headers

**Knowledge-unit ID:** `C23-P00-CH04-S07`  
**Importance:** Critical  
**Memory layers:** Atomic, Conceptual, Procedural, Relationship, Engineering Judgment

### 1. Core idea

`.c` files commonly store implementation definitions and are compiled as translation units, while `.h` files commonly share declarations, types, macros, and interfaces via preprocessing; this separation aids modularity but is not an extension rule mandated by ISO C.

### 2. Mental model

Headers are contracts/interfaces read by source files via `#include`; `.c` source files are where function implementations live. `#include` conceptually inserts header contents at preprocessing time, not making the header a binary module compiled and linked independently.

Limitation of analogy: headers do not automatically become correct contracts. Declarations must match definitions, linkage rules still apply, and include guards only prevent reprocessing of a header within a single translation unit.

### 3. Technical mechanism

**Example project structure**

```text
greet-project/
├── include/
│   └── greet.h
├── src/
│   ├── greet.c
│   └── main.c
└── build/
```

`include/greet.h`:

```c
#ifndef GREET_H
#define GREET_H

void greet(const char *name);

#endif
```

`src/greet.c`:

```c
#include <stddef.h>
#include <stdio.h>
#include "greet.h"

void greet(const char *name)
{
    if (name == NULL) {
        name = "world";
    }

    printf("Hello, %s!\n", name);
}
```

`src/main.c`:

```c
#include "greet.h"

int main(void)
{
    greet("C programmer");
    return 0;
}
```

Headers use include guards so declarations are not processed repeatedly if include paths meet more than once in a single translation unit. `NULL` is defined by the appropriate standard header; since `greet.c` uses `NULL`, a more explicit and portable example includes `<stddef.h>`:

```c
#include <stddef.h>
#include <stdio.h>
#include "greet.h"
```

**Multi-file build — GCC/Clang (POSIX shell)**

From `greet-project/` root:

```sh
mkdir -p build
cc -std=c17 -Wall -Wextra -Wpedantic -Werror   -Iinclude src/main.c src/greet.c -o build/greet
./build/greet
```

Output:

```text
Hello, C programmer!
```

**Multi-file build — MSVC Developer Command Prompt**

```bat
if not exist build mkdir build
cl /nologo /W4 /WX /std:c17 /I include src\main.c src\greet.c /Fe:build\greet.exe
build\greet.exe
```

**Staged build — compile then link**

```sh
cc -std=c17 -Wall -Wextra -Wpedantic -Werror -Iinclude -c src/main.c -o build/main.o
cc -std=c17 -Wall -Wextra -Wpedantic -Werror -Iinclude -c src/greet.c -o build/greet.o
cc build/main.o build/greet.o -o build/greet
```

Headers do not need to be added as separate compilation inputs in the simple commands above; `.c` files that include headers become the translation units processed. Build systems may still record headers as dependencies so header changes trigger rebuilds of relevant sources.

**Common errors and how to read diagnostics**

- `undefined reference to greet` / unresolved external: declaration visible at compile time, but definition not linked, or name/signature/linkage mismatch.
- `implicit declaration` or declaration-not-found diagnostic: header not included, wrong path, or declaration unavailable.
- `multiple definition`: same external definition enters multiple translation units; check if function/object definitions are placed in headers without proper strategy.
- `No such file or directory`: file/header path wrong, file not created, or include search path mismatch.
- Filename capitalization differences may be visible on case-sensitive filesystems even when not on certain Windows configurations.

### 4. Formal boundary

- ISO C defines translation units and preprocessing, not a requirement that source files must be named `.c` and headers `.h`. Those extensions are toolchain conventions.
- `#include` is a preprocessing directive. Included headers affect the translation unit that includes them; headers are not automatically separate link units.
- Include guards are a conventional pattern using preprocessor macros, not a formal ISO C module mechanism.
- Function declarations must be consistent with definitions. Differences in parameter/return type or linkage can cause diagnostics or invalid programs; do not rely on the linker to check all type consistency across translation units.
- `static` on file-scope functions/objects gives internal linkage; non-`static` definitions generally have external linkage unless other rules apply. Linkage details will be studied in function/declaration chapters; do not expand this chapter into a replacement for that material.
- Standard headers use `<stdio.h>` form; project headers usually use `"greet.h"` form. Include search order is implementation-influenced and affected by compiler options. Do not assume identical order across all compilers.
- `#pragma once` is supported by many compilers, but is not a portable replacement for ISO C-based include guards. If using that pragma, record it as an implementation feature.

### 5. Practical consequence

- Place interface declarations together in headers and implementation definitions in `.c` files unless there is a clear technical reason.
- Do not put ordinary external function definitions in headers included by many `.c` files; it can cause multiple definitions.
- Include headers that declare every function/library used. Avoid relying on implicit declarations or transitive headers.
- Use unique and consistent include guards.
- Build all translation units and link together; successful compilation of one file does not prove the multi-file project can link.
- Make the compiler command the source of truth for configuration. Editors and build systems must follow the same include path, macros, and flags.

**Pitfall box**

> **Headers are not "implementation files that automatically get compiled."** `#include "greet.h"` makes header contents part of the translation unit being processed. If `greet.c` is not included in the link command, the `greet` declaration alone does not provide the function definition.

## Standards and source-verification notes

### Scope of standards claims

- Platform installation steps are external-tool documentation, not ISO C requirements.
- ISO C's translation model and preprocessing concepts are relevant to 0.4.7; exact clause numbering should be checked against licensed ISO/IEC 9899:2024 text before publishing clause-level normative citations. **Exact C23 clause references: to be verified with authoritative source.**
- No unsupported claim of complete C23 implementation conformance is made.
- Compiler support tables describe implementation feature status and may change between releases. Recheck version in use.
- Shell commands are platform examples. Their availability and behavior are determined by shell/OS/package manager, not ISO C.
