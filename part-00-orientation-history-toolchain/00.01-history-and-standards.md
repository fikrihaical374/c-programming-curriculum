> **Big picture:** C is not a frozen snapshot. It is a language family that has evolved through standard editions, amendments, corrigenda, and technical documents. When you read or write portable code, do not ask only, “Does my compiler accept this syntax?” Ask **“Which C version am I targeting, what does that version guarantee, and which document supports the claim?”**

## How to use this chapter

This chapter introduces C history and standards literacy. It is not an exhaustive catalog of every change in every edition. The feature lists are selected to build a useful mental model. When a normative detail affects program correctness, consult the applicable edition of the standard and record the exact clause.

The chapter consistently distinguishes three kinds of evidence:

1. **Historical and publication facts** — dates, document names, and relationships among editions, supported by relevant WG14, ISO, or implementation records.
2. **Feature summaries** — educational maps of important changes; these do not replace normative text.
3. **Normative requirements** — requirements that must be verified against the cited edition of ISO/IEC 9899. If a clause has not been checked directly, mark it **to be verified with an authoritative source** rather than guessing.

### Timeline at a glance

| Period / name | Document identity | Remember it as |
|---|---|---|
| 1969–early 1970s | B, NB, and then C at Bell Labs | Historical roots and the needs of Unix systems programming |
| 1978 | *The C Programming Language*, first edition (Kernighan and Ritchie) | An influential description of pre-ANSI C; not an ISO standard |
| 1989 | ANSI X3.159-1989 | The first ANSI standardization, commonly called C89 |
| 1990 | ISO/IEC 9899:1990 | The ISO adoption, commonly called C90 |
| 1995 | ISO/IEC 9899:1990/Amd 1:1995 | Amendment 1, commonly called C95 |
| 1999 | ISO/IEC 9899:1999 | C99 |
| 2011 | ISO/IEC 9899:2011 | C11 |
| 2018 | ISO/IEC 9899:2018 | C17 or C18; a corrected edition of C11 |
| 2024 | ISO/IEC 9899:2024 | C23, the fifth edition of the C standard |
| After the C23 cycle | WG14 work on the next generation | Future proposals and drafts; not part of C23 |

**Do not memorize dates without understanding the relationships.** Reconstruct the sequence: K&R described early C practice → ANSI standardized the language → ISO published an international adoption → amendments and corrigenda corrected or extended the documents → major revisions introduced broader changes → drafts for the next generation remained outside the already published edition.

## 0.2.1 — The B and NB languages, the development of C, and the first K&R book

**Knowledge-unit ID:** `C23-P00-CH02-S01`  
**Importance:** Core  
**Memory layers:** Atomic · Conceptual · Relationship  
**Prerequisite:** `0.1` (programming environment and context)

### 1. Core idea

C developed at Bell Labs from earlier languages—especially B and NB—to meet the needs of systems programming with a language that could express low-level operations while remaining practical and structured.

### 2. Mental model

Think of C as an answer to the systems-engineering needs of its time. The language had to remain close enough to the machine for systems software while providing more structure and expressive power than earlier approaches.

This analogy explains the *motivation*, not the language specification. Do not conclude that C is merely “assembly with more convenient syntax.” C has its own semantics for objects, types, expressions, and abstraction.

### 3. Technical mechanism

- **B** was developed by Ken Thompson at Bell Labs and used in early Unix work. B descended from BCPL and had a simpler model than C.
- **NB (New B)** is a name found in the history of the development that led to C. It is not a formal edition of a language standard.
- **C** was developed by Dennis Ritchie at Bell Labs in the early 1970s. Important developments included a richer type system and facilities better suited to implementing Unix across different machines.
- C later became the primary language for Unix development. The historical relationship between C and Unix is important, but C does not define Unix, and Unix does not define C.
- In 1978, Brian W. Kernighan and Dennis M. Ritchie published the first edition of *The C Programming Language*. The book became an influential description and distribution channel for C before ANSI standardization.

Historical example: programs based on the first K&R edition may use idioms and declaration forms that standardization later changed or tightened. Therefore, “appears in the K&R book” does not automatically mean “conforms to C23.”

### 4. Formal boundary

- This period predates the formal ISO C editions beginning with C89/C90.
- The first K&R book is a historical and technical reference, **not** an ISO/IEC 9899 document.
- Early compiler practices were not uniform. Do not assume that all early implementations accepted identical features.
- The history of B, NB, and C is not a basis for inferring normative C23 requirements. For historical claims more specific than this summary—such as exact dates of individual changes or the origin of a particular feature—consult primary historical sources. If a claim has not been checked, mark it **to be verified with an authoritative source**.

### 5. Practical consequence

When reading legacy code, first identify its era and intended dialect. Do not immediately “fix” it under the assumption that it was written for C23. Distinguish among:

- K&R style as a historical practice;
- an old compiler dialect as implementation behavior; and
- a published standard as a formal language contract.

### 6. Retrieval question

Without looking at your notes, explain why C followed B/NB, describe Unix's role in its history, and explain why the first K&R book is important but is not an ISO standard.

## 0.2.2 — K&R C and the transition to ANSI standardization

**Knowledge-unit ID:** `C23-P00-CH02-S02`  
**Importance:** Core  
**Memory layers:** Atomic · Conceptual · Relationship · Engineering Judgment

### 1. Core idea

K&R C describes influential C practice before formal standardization. ANSI standardization was needed to give programmers and compiler developers a more consistent shared reference.

### 2. Mental model

Treat K&R C as an *influential map of practice* and the ANSI/ISO standard as a *publicly agreed contract*. The practice map helps explain history; the standard contract determines conformance claims.

The analogy has limits. A standard does not guarantee that every compiler is free of bugs or that every program behaves identically on every machine. It specifies requirements and the behavior boundaries for conforming implementations.

### 3. Technical mechanism

Before ANSI C, C implementations evolved across a diverse ecosystem of compilers and systems. The first K&R book helped spread common idioms, but it could not resolve every implementation difference.

Example of an old-style K&R function definition:

```c
int add(a, b)
int a;
int b;
{
    return a + b;
}
```

The parameter declarations appear after the parameter list. A prototype-style declaration, which became the standard modern idiom, looks like this:

```c
int add(int a, int b);
```

A prototype provides parameter type information at the declaration point. The first example is a historical illustration; its acceptance and diagnostics depend on the language version and implementation.

ANSI standardization through committee X3J11 produced ANSI X3.159-1989. Its purpose was not merely to unify syntax. It also defined the language and standard library more systematically.

### 4. Formal boundary

- **K&R C** usually refers to C as described before ANSI C, especially in the first K&R book. It does not identify a particular ISO edition.
- ANSI X3.159-1989 is the ANSI standard. Do not call it ISO/IEC 9899:1990 without explaining the adoption relationship.
- Function prototypes, `void`, `const`, and `volatile` were important parts of the transition to ANSI C. Verify formal details in the relevant C89/C90 standard text.
- Do not equate “the compiler accepts the old form” with “the form is recommended for new programs.”

### 5. Practical consequence

For new code, use function declarations with prototypes and set the language standard explicitly in the build. For legacy code, document the target dialect before changing function declarations. During review, ask whether the code depends on pre-ANSI rules, compiler extensions, or a specific standard edition.

### 6. Retrieval question

What problem did ANSI standardization address? How does the role of the K&R book differ from the role of the ANSI standard as a conformance reference?

## 0.2.3 — ANSI X3.159-1989, ISO C90, and technical corrections

**Knowledge-unit ID:** `C23-P00-CH02-S03`  
**Importance:** Core  
**Memory layers:** Atomic · Relationship · Standards literacy

### 1. Core idea

ANSI X3.159-1989 was the first ANSI C standard. ISO/IEC 9899:1990 was its international adoption and is commonly called C90. Later correction documents fixed errors without creating a new major language revision.

### 2. Mental model

Think of the 1989 ANSI standard as the source document later adopted by ISO in 1990. The core technical content was the same, although section numbering was adjusted in the ISO publication. A corrigendum then works like an official erratum: it corrects text that is erroneous or ambiguous; it does not automatically add a new generation of features.

### 3. Technical mechanism

- **ANSI X3.159-1989** was approved in 1989 and is widely known as **C89** or ANSI C.
- ISO later published **ISO/IEC 9899:1990**, commonly called **C90**.
- GCC documentation states that there is no technical difference between the ANSI and ISO publications; ANSI section numbers were renumbered as clauses in the ISO document.
- ISO C90 later received two Technical Corrigenda, published in 1994 and 1996.
- Amendment 1 in 1995 was a separate additional change and is covered in the next subchapter.

A compact timeline is: `C89 (ANSI, 1989) → C90 (ISO, 1990) → corrigenda (1994/1996), with Amendment 1 (1995)`.

### 4. Formal boundary

- **C89** and **C90** are often used almost interchangeably in technical conversation, but the names refer to different publication bodies and years.
- A Technical Corrigendum is not the same as a full revision such as C99 or C11.
- Keep the chronology straight: the first C90 corrigendum appeared in 1994, Amendment 1 in 1995, and the second corrigendum in 1996. Do not label Amendment 1 as the “second correction.”
- Compiler documentation can explain dialect support, but it does not replace the standard when interpreting normative requirements.

### 5. Practical consequence

When a source says “ANSI C,” determine whether it means C89/C90 or merely a compiler-supported dialect. To target C90, select C90 explicitly and request strict diagnostics. Do not use `-std=gnu90` and then claim that all GNU extensions are ISO C90.

## 0.2.4 — C95 Amendment 1: wide characters, digraphs, and related facilities

**Knowledge-unit ID:** `C23-P00-CH02-S04`  
**Importance:** Supporting  
**Memory layers:** Atomic · Conceptual · Standards literacy

### 1. Core idea

C95 is C90 as extended by the 1995 Amendment 1. The amendment focused heavily on international character support and added related language and library facilities.

### 2. Mental model

C90 is the foundation; Amendment 1 adds a defined set of capabilities without replacing the entire edition with a major revision such as C99. Think of C95 as “C90 plus an amendment,” not as a completely separate language.

This model explains the document relationship only. To determine whether a particular feature belongs to the core language, preprocessing, or library, consult the amendment and the consolidated standard text.

### 3. Technical mechanism

Well-known Amendment 1 changes include:

- **Wide-character support** and related multibyte/wide-character facilities for processing characters beyond the basic character model commonly used in early C.
- Library headers and facilities such as `<wchar.h>` and `<wctype.h>` for wide-character operations and character classification/conversion.
- **Digraphs**, alternative spellings for certain tokens that can be useful when particular graphic characters are difficult to type or unavailable in an environment.
- The `__STDC_VERSION__` macro, which helps identify the language standard version supported by an implementation. Interpret its value according to the relevant language version and implementation; do not assume every older compiler defines it in the same way.

Digraph example:

```c
#include <stdio.h>

int main(void)
<%
    puts("C95 digraph example");
    return 0;
%>
```

In the specified C token contexts, `<%` and `%>` are alternative spellings for `{` and `}`. A compiler supporting C95 or a later standard should recognize them; verify support in the compiler configuration used for a particular build.

### 4. Formal boundary

- C95 is not the name of a new ISO publication replacing ISO/IEC 9899:1990. It commonly refers to C90 as modified by Amendment 1.
- A wide character is not synonymous with “every text character is a Unicode code point.” Encoding, locale, representation, and conversion still have their own rules and limits.
- A digraph is an alternative token spelling, not a new operator with different semantics.
- Wide-character facilities must not be confused with full support for every encoding or every modern text-processing requirement.

### 5. Practical consequence

When reading legacy code, recognize digraphs as valid token spellings in language versions that support them. When processing multibyte or wide-character text, do not assume that one `wchar_t` always represents one visible Unicode character or one byte. Choose APIs and encodings based on the actual platform and library contracts.

### 6. Retrieval question

How is C95 related to C90? What is the general purpose of wide-character facilities, and why does a digraph not change the meaning of the token it represents?

## 0.2.5 — C99: language and library changes

**Knowledge-unit ID:** `C23-P00-CH02-S05`  
**Importance:** Critical  
**Memory layers:** Atomic · Conceptual · Procedural · Relationship

### 1. Core idea

C99 was a major ISO C revision that expanded expressions, numeric types, declarations, and the standard library. It gave modern C code facilities that were not available in C90.

### 2. Mental model

C99 is not “C90 with a few extra keywords.” It expands several layers at once: expression syntax, object declarations, available numeric types, and library APIs. Selecting C90 mode is therefore not equivalent to selecting C99 mode.

### 3. Technical mechanism

Important C99 changes include the following. This is a selected overview, not a complete inventory.

| Area | Example C99 facility | What to recognize |
|---|---|---|
| Comments | `//` | Single-line comments became part of the standard language |
| Integer types | `long long`, `<stdint.h>`, `<inttypes.h>` | Additional integer choices, exact-width types where provided, and related format macros |
| Declarations | Declarations may appear after statements within a block | More flexible declaration placement |
| Arrays | Variable-length arrays (VLAs) | In permitted contexts, an automatic array size may depend on a runtime expression |
| Initialization | Designated initializers, such as `.x = 3` | Select fields or elements by designator |
| Expressions | Compound literals | Create unnamed objects using typed literal syntax |
| Functions | `inline`, `restrict` | Facilities related to function linkage/optimization and aliasing contracts |
| Numeric types | `_Bool`, complex types, additional floating-point facilities | A richer set of numeric expressions and types |
| Library | `snprintf`, `<stdbool.h>`, `<stdint.h>`, `<inttypes.h>`, and others | Expanded standard APIs |

Designated initializer example:

```c
#include <stdio.h>

struct Point {
    int x;
    int y;
};

int main(void)
{
    struct Point p = { .y = 8, .x = 3 };
    printf("(%d, %d)\n", p.x, p.y);
    return 0;
}
```

VLA example (use only with implementations and language versions that support the feature; VLA support is not universal in every implementation context):

```c
#include <stddef.h>

int sum(size_t n, const int values[n])
{
    int total = 0;

    for (size_t i = 0; i < n; ++i) {
        total += values[i];
    }
    return total;
}
```

VLA is a C99 feature with support requirements that must be considered in later revisions. Do not assume that every compiler, target, or freestanding environment supports all VLA functionality.

### 4. Formal boundary

- C99 was published as ISO/IEC 9899:1999.
- C99 later received three Technical Corrigenda: 2001, 2004, and 2007.
- Not every C99 feature is required in every implementation context. Check optional or conditionally supported features and the distinction between hosted and freestanding implementations.
- `restrict` is not a compiler instruction that automatically proves aliasing is safe. It establishes a semantic contract; violating that contract can result in undefined behavior.
- Do not generalize VLA into the claim that “all C arrays have runtime sizes.”
- Verify the requirements of each feature against ISO/IEC 9899:1999 and the relevant corrigenda, or against the C23 edition when asking about current rules.

### 5. Practical consequence

If a project targets C99 or later, use C99 features deliberately and document the minimum compiler version. If portability to embedded or freestanding compilers matters, audit the VLA, complex-number, and library facilities you use. For integers that require a particular width, evaluate `<stdint.h>` and the availability of `intN_t`/`uintN_t` types. Do not assume that `int` has the same width on every target.
