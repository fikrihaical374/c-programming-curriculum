The publicly available WG14 N3220 document is a draft/reference document, not a substitute for the published ISO standard.

> **Big picture:** C is not a frozen snapshot. It is a language family that has evolved through standard editions, amendments, corrigenda, and technical documents. When you read or write portable code, do not ask only, “Does my compiler accept this syntax?” Ask **“Which C version am I targeting, what does that version guarantee, and which document supports the claim?”**

## How to use this chapter

This chapter introduces C history and standards literacy. It is not an exhaustive catalog of every change in every edition. The feature lists are selected to build a useful mental model. When a normative detail affects program correctness, consult the applicable edition of the standard and record the exact clause.

The chapter consistently distinguishes three kinds of evidence:

1. **Historical and publication facts** — dates, document names, and relationships among editions, supported by relevant WG14, ISO, or implementation records.
2. **Feature summaries** — educational maps of important changes; these do not replace normative text.
3. **Normative requirements** — requirements that must be verified against the cited edition of ISO/IEC 9899. If a clause has not been checked directly, mark it **to be verified with an authoritative source** rather than guessing.

### Timeline at a glance

| Period / name | Document identity | Remember it as |
|---|---|---|
| 1969–early 1970s | B, NB, and then C at Bell Labs | Historical roots and the needs of Unix systems programming |
| 1978 | *The C Programming Language*, first edition (Kernighan and Ritchie) | An influential description of pre-ANSI C; not an ISO standard |
| 1989 | ANSI X3.159-1989 | The first ANSI standardization, commonly called C89 |
| 1990 | ISO/IEC 9899:1990 | The ISO adoption, commonly called C90 |
| 1995 | ISO/IEC 9899:1990/Amd 1:1995 | Amendment 1, commonly called C95 |
| 1999 | ISO/IEC 9899:1999 | C99 |
| 2011 | ISO/IEC 9899:2011 | C11 |
| 2018 | ISO/IEC 9899:2018 | C17 or C18; a corrected edition of C11 |
| 2024 | ISO/IEC 9899:2024 | C23, the fifth edition of the C standard |
| After the C23 cycle | WG14 work on the next generation | Future proposals and drafts; not part of C23 |

**Do not memorize dates without understanding the relationships.** Reconstruct the sequence: K&R described early C practice → ANSI standardized the language → ISO published an international adoption → amendments and corrigenda corrected or extended the documents → major revisions introduced broader changes → drafts for the next generation remained outside the already published edition.

## 0.2.1 — The B and NB languages, the development of C, and the first K&R book

**Knowledge-unit ID:** `C23-P00-CH02-S01`  
**Importance:** Core  
**Memory layers:** Atomic · Conceptual · Relationship  
**Prerequisite:** `0.1` (programming environment and context)

### 1. Core idea

C developed at Bell Labs from earlier languages—especially B and NB—to meet the needs of systems programming with a language that could express low-level operations while remaining practical and structured.

### 2. Mental model

Think of C as an answer to the systems-engineering needs of its time. The language had to remain close enough to the machine for systems software while providing more structure and expressive power than earlier approaches.

This analogy explains the *motivation*, not the language specification. Do not conclude that C is merely “assembly with more convenient syntax.” C has its own semantics for objects, types, expressions, and abstraction.

### 3. Technical mechanism

- **B** was developed by Ken Thompson at Bell Labs and used in early Unix work. B descended from BCPL and had a simpler model than C.
- **NB (New B)** is a name found in the history of the development that led to C. It is not a formal edition of a language standard.
- **C** was developed by Dennis Ritchie at Bell Labs in the early 1970s. Important developments included a richer type system and facilities better suited to implementing Unix across different machines.
- C later became the primary language for Unix development. The historical relationship between C and Unix is important, but C does not define Unix, and Unix does not define C.
- In 1978, Brian W. Kernighan and Dennis M. Ritchie published the first edition of *The C Programming Language*. The book became an influential description and distribution channel for C before ANSI standardization.

Historical example: programs based on the first K&R edition may use idioms and declaration forms that standardization later changed or tightened. Therefore, “appears in the K&R book” does not automatically mean “conforms to C23.”

### 4. Formal boundary

- This period predates the formal ISO C editions beginning with C89/C90.
- The first K&R book is a historical and technical reference, **not** an ISO/IEC 9899 document.
- Early compiler practices were not uniform. Do not assume that all early implementations accepted identical features.
- The history of B, NB, and C is not a basis for inferring normative C23 requirements. For historical claims more specific than this summary—such as exact dates of individual changes or the origin of a particular feature—consult primary historical sources. If a claim has not been checked, mark it **to be verified with an authoritative source**.

### 5. Practical consequence

When reading legacy code, first identify its era and intended dialect. Do not immediately “fix” it under the assumption that it was written for C23. Distinguish among:

- K&R style as a historical practice;
- an old compiler dialect as implementation behavior; and
- a published standard as a formal language contract.

### 6. Retrieval question

Without looking at your notes, explain why C followed B/NB, describe Unix's role in its history, and explain why the first K&R book is important but is not an ISO standard.

**Retrieval item ID:** `C23-P00-CH02-S01-RET-01`  
**Candidate misconception ID:** `MIS-P00-CH02-S01-01`

## 0.2.2 — K&R C and the transition to ANSI standardization

**Knowledge-unit ID:** `C23-P00-CH02-S02`  
**Importance:** Core  
**Memory layers:** Atomic · Conceptual · Relationship · Engineering Judgment

### 1. Core idea

K&R C describes influential C practice before formal standardization. ANSI standardization was needed to give programmers and compiler developers a more consistent shared reference.

### 2. Mental model

Treat K&R C as an *influential map of practice* and the ANSI/ISO standard as a *publicly agreed contract*. The practice map helps explain history; the standard contract determines conformance claims.

The analogy has limits. A standard does not guarantee that every compiler is free of bugs or that every program behaves identically on every machine. It specifies requirements and the behavior boundaries for conforming implementations.

### 3. Technical mechanism

Before ANSI C, C implementations evolved across a diverse ecosystem of compilers and systems. The first K&R book helped spread common idioms, but it could not resolve every implementation difference.

Example of an old-style K&R function definition:

```c
int add(a, b)
int a;
int b;
{
    return a + b;
}
```

The parameter declarations appear after the parameter list. A prototype-style declaration, which became the standard modern idiom, looks like this:

```c
int add(int a, int b);
```

A prototype provides parameter type information at the declaration point. The first example is a historical illustration; its acceptance and diagnostics depend on the language version and implementation.

ANSI standardization through committee X3J11 produced ANSI X3.159-1989. Its purpose was not merely to unify syntax. It also defined the language and standard library more systematically.

### 4. Formal boundary

- **K&R C** usually refers to C as described before ANSI C, especially in the first K&R book. It does not identify a particular ISO edition.
- ANSI X3.159-1989 is the ANSI standard. Do not call it ISO/IEC 9899:1990 without explaining the adoption relationship.
- Function prototypes, `void`, `const`, and `volatile` were important parts of the transition to ANSI C. Verify formal details in the relevant C89/C90 standard text.
- Do not equate “the compiler accepts the old form” with “the form is recommended for new programs.”

### 5. Practical consequence

For new code, use function declarations with prototypes and set the language standard explicitly in the build. For legacy code, document the target dialect before changing function declarations. During review, ask whether the code depends on pre-ANSI rules, compiler extensions, or a specific standard edition.

### 6. Retrieval question

What problem did ANSI standardization address? How does the role of the K&R book differ from the role of the ANSI standard as a conformance reference?

**Retrieval item ID:** `C23-P00-CH02-S02-RET-01`  
**Candidate misconception ID:** `MIS-P00-CH02-S02-01`

**Contrastive retrieval:** Why does `int f(int);` provide information that an old-style `int f();` declaration does not provide in dialects that distinguish the two? State which language version you are discussing.

## 0.2.3 — ANSI X3.159-1989, ISO C90, and technical corrections

**Knowledge-unit ID:** `C23-P00-CH02-S03`  
**Importance:** Core  
**Memory layers:** Atomic · Relationship · Standards literacy

### 1. Core idea

ANSI X3.159-1989 was the first ANSI C standard. ISO/IEC 9899:1990 was its international adoption and is commonly called C90. Later correction documents fixed errors without creating a new major language revision.

### 2. Mental model

Think of the 1989 ANSI standard as the source document later adopted by ISO in 1990. The core technical content was the same, although section numbering was adjusted in the ISO publication. A corrigendum then works like an official erratum: it corrects text that is erroneous or ambiguous; it does not automatically add a new generation of features.

### 3. Technical mechanism

- **ANSI X3.159-1989** was approved in 1989 and is widely known as **C89** or ANSI C.
- ISO later published **ISO/IEC 9899:1990**, commonly called **C90**.
- GCC documentation states that there is no technical difference between the ANSI and ISO publications; ANSI section numbers were renumbered as clauses in the ISO document.
- ISO C90 later received two Technical Corrigenda, published in 1994 and 1996.
- Amendment 1 in 1995 was a separate additional change and is covered in the next subchapter.

A compact timeline is: `C89 (ANSI, 1989) → C90 (ISO, 1990) → corrigenda (1994/1996), with Amendment 1 (1995)`.

### 4. Formal boundary

- **C89** and **C90** are often used almost interchangeably in technical conversation, but the names refer to different publication bodies and years.
- A Technical Corrigendum is not the same as a full revision such as C99 or C11.
- Keep the chronology straight: the first C90 corrigendum appeared in 1994, Amendment 1 in 1995, and the second corrigendum in 1996. Do not label Amendment 1 as the “second correction.”
- Compiler documentation can explain dialect support, but it does not replace the standard when interpreting normative requirements.

### 5. Practical consequence

When a source says “ANSI C,” determine whether it means C89/C90 or merely a compiler-supported dialect. To target C90, select C90 explicitly and request strict diagnostics. Do not use `-std=gnu90` and then claim that all GNU extensions are ISO C90.

### 6. Retrieval question

Reconstruct the relationship between ANSI X3.159-1989 and ISO/IEC 9899:1990. What do Technical Corrigenda do, and how did the 1995 Amendment 1 differ?

**Retrieval item ID:** `C23-P00-CH02-S03-RET-01`

## 0.2.4 — C95 Amendment 1: wide characters, digraphs, and related facilities

**Knowledge-unit ID:** `C23-P00-CH02-S04`  
**Importance:** Supporting  
**Memory layers:** Atomic · Conceptual · Standards literacy

### 1. Core idea

C95 is C90 as extended by the 1995 Amendment 1. The amendment focused heavily on international character support and added related language and library facilities.

### 2. Mental model

C90 is the foundation; Amendment 1 adds a defined set of capabilities without replacing the entire edition with a major revision such as C99. Think of C95 as “C90 plus an amendment,” not as a completely separate language.

This model explains the document relationship only. To determine whether a particular feature belongs to the core language, preprocessing, or library, consult the amendment and the consolidated standard text.

### 3. Technical mechanism

Well-known Amendment 1 changes include:

- **Wide-character support** and related multibyte/wide-character facilities for processing characters beyond the basic character model commonly used in early C.
- Library headers and facilities such as `<wchar.h>` and `<wctype.h>` for wide-character operations and character classification/conversion.
- **Digraphs**, alternative spellings for certain tokens that can be useful when particular graphic characters are difficult to type or unavailable in an environment.
- The `__STDC_VERSION__` macro, which helps identify the language standard version supported by an implementation. Interpret its value according to the relevant language version and implementation; do not assume every older compiler defines it in the same way.

Digraph example:

```c
#include <stdio.h>

int main(void)
<%
    puts("C95 digraph example");
    return 0;
%>
```

In the specified C token contexts, `<%` and `%>` are alternative spellings for `{` and `}`. A compiler supporting C95 or a later standard should recognize them; verify support in the compiler configuration used for a particular build.

### 4. Formal boundary

- C95 is not the name of a new ISO publication replacing ISO/IEC 9899:1990. It commonly refers to C90 as modified by Amendment 1.
- A wide character is not synonymous with “every text character is a Unicode code point.” Encoding, locale, representation, and conversion still have their own rules and limits.
- A digraph is an alternative token spelling, not a new operator with different semantics.
- Wide-character facilities must not be confused with full support for every encoding or every modern text-processing requirement.

### 5. Practical consequence

When reading legacy code, recognize digraphs as valid token spellings in language versions that support them. When processing multibyte or wide-character text, do not assume that one `wchar_t` always represents one visible Unicode character or one byte. Choose APIs and encodings based on the actual platform and library contracts.

### 6. Retrieval question

How is C95 related to C90? What is the general purpose of wide-character facilities, and why does a digraph not change the meaning of the token it represents?

**Retrieval item ID:** `C23-P00-CH02-S04-RET-01`  
**Candidate misconception ID:** `MIS-P00-CH02-S04-01`

## 0.2.5 — C99: language and library changes

**Knowledge-unit ID:** `C23-P00-CH02-S05`  
**Importance:** Critical  
**Memory layers:** Atomic · Conceptual · Procedural · Relationship

### 1. Core idea

C99 was a major ISO C revision that expanded expressions, numeric types, declarations, and the standard library. It gave modern C code facilities that were not available in C90.

### 2. Mental model

C99 is not “C90 with a few extra keywords.” It expands several layers at once: expression syntax, object declarations, available numeric types, and library APIs. Selecting C90 mode is therefore not equivalent to selecting C99 mode.

### 3. Technical mechanism

Important C99 changes include the following. This is a selected overview, not a complete inventory.

| Area | Example C99 facility | What to recognize |
|---|---|---|
| Comments | `//` | Single-line comments became part of the standard language |
| Integer types | `long long`, `<stdint.h>`, `<inttypes.h>` | Additional integer choices, exact-width types where provided, and related format macros |
| Declarations | Declarations may appear after statements within a block | More flexible declaration placement |
| Arrays | Variable-length arrays (VLAs) | In permitted contexts, an automatic array size may depend on a runtime expression |
| Initialization | Designated initializers, such as `.x = 3` | Select fields or elements by designator |
| Expressions | Compound literals | Create unnamed objects using typed literal syntax |
| Functions | `inline`, `restrict` | Facilities related to function linkage/optimization and aliasing contracts |
| Numeric types | `_Bool`, complex types, additional floating-point facilities | A richer set of numeric expressions and types |
| Library | `snprintf`, `<stdbool.h>`, `<stdint.h>`, `<inttypes.h>`, and others | Expanded standard APIs |

Designated initializer example:

```c
#include <stdio.h>

struct Point {
    int x;
    int y;
};

int main(void)
{
    struct Point p = { .y = 8, .x = 3 };
    printf("(%d, %d)\n", p.x, p.y);
    return 0;
}
```

VLA example (use only with implementations and language versions that support the feature; VLA support is not universal in every implementation context):

```c
#include <stddef.h>

int sum(size_t n, const int values[n])
{
    int total = 0;

    for (size_t i = 0; i < n; ++i) {
        total += values[i];
    }
    return total;
}
```

VLA is a C99 feature with support requirements that must be considered in later revisions. Do not assume that every compiler, target, or freestanding environment supports all VLA functionality.

### 4. Formal boundary

- C99 was published as ISO/IEC 9899:1999.
- C99 later received three Technical Corrigenda: 2001, 2004, and 2007.
- Not every C99 feature is required in every implementation context. Check optional or conditionally supported features and the distinction between hosted and freestanding implementations.
- `restrict` is not a compiler instruction that automatically proves aliasing is safe. It establishes a semantic contract; violating that contract can result in undefined behavior.
- Do not generalize VLA into the claim that “all C arrays have runtime sizes.”
- Verify the requirements of each feature against ISO/IEC 9899:1999 and the relevant corrigenda, or against the C23 edition when asking about current rules.

### 5. Practical consequence

If a project targets C99 or later, use C99 features deliberately and document the minimum compiler version. If portability to embedded or freestanding compilers matters, audit the VLA, complex-number, and library facilities you use. For integers that require a particular width, evaluate `<stdint.h>` and the availability of `intN_t`/`uintN_t` types. Do not assume that `int` has the same width on every target.

### 6. Retrieval question

Name four areas changed by C99, give one feature example for each, and explain one portability limit that must be checked before relying on it.

**Retrieval item ID:** `C23-P00-CH02-S05-RET-01`

## 0.2.6 — C11: atomics, threads, alignment, and library changes

**Knowledge-unit ID:** `C23-P00-CH02-S06`  
**Importance:** Critical  
**Memory layers:** Atomic · Conceptual · Procedural · Relationship · Engineering Judgment

### 1. Core idea

C11 introduced a more explicit language and library model for concurrency, atomic operations, alignment, generic selection, and other supporting facilities.

### 2. Mental model

Before C11, programmers often relied on platform or compiler contracts to build concurrent programs. C11 provided standard language facilities for some of these needs: atomics govern operations on atomic objects, while thread and synchronization facilities provide thread-management APIs when an implementation supports them.

Do not equate “atomic facilities exist” with “all memory accesses are safe.” Atomics, mutexes, memory ordering, and data races are distinct concepts that must be analyzed together.

### 3. Technical mechanism

Important C11 facilities include:

- **`_Atomic` and `<stdatomic.h>`:** atomic types and operations, including load, store, exchange, and read-modify-write operations with memory-order options.
- **`<threads.h>`:** thread, mutex, condition-variable, and related APIs.
- **Alignment:** `_Alignas`, `_Alignof`, and related facilities for specifying or querying alignment.
- **`_Static_assert`:** a condition checked during translation.
- **`_Generic`:** generic selection based on the type of a controlling expression.
- **Anonymous structures and unions** in the contexts specified by the standard.
- **`_Noreturn`**, certain Unicode character/string literal support, and other library changes.

Minimal atomic example:

```c
#include <stdatomic.h>
#include <stdio.h>

int main(void)
{
    atomic_int counter = ATOMIC_VAR_INIT(0);

    atomic_fetch_add_explicit(&counter, 1, memory_order_relaxed);

    printf("%d\n", atomic_load_explicit(&counter, memory_order_relaxed));
    return 0;
}
```

This program demonstrates atomic operations on one object. `memory_order_relaxed` guarantees atomicity for those operations, but it does **not** by itself establish a synchronization relationship for publishing other data.

### C23-compatible lab: atomic operations

```c
#include <stdatomic.h>
#include <stdio.h>

int main(void)
{
    atomic_int count;
    atomic_init(&count, 0);
    atomic_fetch_add_explicit(&count, 1, memory_order_relaxed);
    printf("count = %d\n", atomic_load_explicit(&count, memory_order_relaxed));
    return 0;
}
```

Compile: `gcc -std=c23 -pedantic-errors -Wall -Wextra -Werror c11_atomic.c -o c11_atomic`.

This single-threaded lab checks atomic syntax and operations. It does not demonstrate inter-thread synchronization or prove that the complete program is race-free.

### 4. Formal boundary

- Thread facilities and some atomic support may be optional or implementation-dependent. Check support macros, standard requirements, and toolchain documentation.
- Atomics do not automatically mean lock-free. Lock-free behavior is a property to verify, not assume.
- `memory_order_relaxed` does not provide inter-thread synchronization ordering.
- A data race on a non-atomic object accessed without appropriate synchronization remains a serious problem. Do not conclude that “the program is safe because one variable is atomic.”
- Alignment concerns object layout and access requirements; it is not synonymous with object size.
- Normative reference: ISO/IEC 9899:2011, especially the relevant memory-model, concurrency, alignment, and library provisions. Exact subclause references for detailed claims are **to be verified with an authoritative source** before use as normative citations.

### 5. Practical consequence

When selecting C11:

1. Check support in both the compiler and the target library/runtime.
2. Identify which objects actually need to be atomic.
3. Determine the required synchronization relationship. Do not choose `memory_order_relaxed` merely because it appears faster.
4. Test on the actual target, including freestanding or embedded configurations when relevant.
5. Document whether threads and atomics are mandatory project requirements or optional facilities.

### 6. Retrieval question

How do atomics, the thread API, and alignment serve different purposes in C11? Why does an `atomic_int` using `memory_order_relaxed` not automatically make an entire concurrent program safe?

**Retrieval item ID:** `C23-P00-CH02-S06-RET-01`  
**Candidate misconception ID:** `MIS-P00-CH02-S06-01`

### Atomicity is not synchronization

Atomicity answers whether an operation on an atomic object is indivisible with respect to the atomic model. Synchronization answers whether operations in different threads establish an ordering relationship. These questions are related, but they are not interchangeable.

Consider a publication pattern with a payload and a flag:

```c
#include <stdatomic.h>

static int payload;
static atomic_int ready;

/* Producer thread */
static void produce(void)
{
    payload = 42;
    atomic_store_explicit(&ready, 1, memory_order_release);
}

/* Consumer thread */
static int consume(void)
{
    if (atomic_load_explicit(&ready, memory_order_acquire) == 1) {
        return payload;
    }
    return -1;
}
```

The intended reasoning is that a release store and an acquire load that reads from that release sequence can establish the required synchronization. The example is a teaching fragment, not a complete thread-creation program. A production implementation must also establish that the consumer actually observes the publication and must handle initialization and object lifetime correctly.

Do not replace the release/acquire pair with relaxed operations while keeping the same reasoning about `payload`. Relaxed operations preserve atomicity of `ready`; they do not, by themselves, publish the non-atomic payload.

## 0.2.7 — C17/C18: corrections and clarifications to C11

**Knowledge-unit ID:** `C23-P00-CH02-S07`  
**Importance:** Core  
**Memory layers:** Atomic · Relationship · Standards literacy

### 1. Core idea

C17/C18 is the ISO/IEC 9899:2018 publication, which primarily integrates corrections and clarifications to C11. It is not a major feature revision that introduces an entirely new generation of the language.

### 2. Mental model

Treat C11 as the baseline edition and C17/C18 as a version that refines and corrects its text. A difference visible in a compiler's standard-version macro or behavior must not immediately be interpreted as a major language change.

### 3. Technical mechanism

- The publication is **ISO/IEC 9899:2018**.
- Both **C17** and **C18** are used in the community. C17 often refers to the revision cycle or 2017 target, while C18 reflects the ISO publication year, 2018.
- WG14 records C17 as published in 2018.
- GCC explains that the corrected version was prepared in 2017 and published in 2018. Corrections are also applied when using `-std=c11`, while the `__STDC_VERSION__` value distinguishes the modes.
- The main focus is defect fixes and clarifications, not new language features on the scale of the C99 or C11 transitions.

### C23-compatible lab: inspect the selected language mode

```c
#include <stdio.h>

int main(void)
{
#ifdef __STDC_VERSION__
    printf("version macro = %ld\n", (long)__STDC_VERSION__);
#else
    puts("version macro is not defined");
#endif
    return 0;
}
```

Compile: `gcc -std=c23 -pedantic-errors -Wall -Wextra -Werror c17_mode_probe.c -o c17_mode_probe`.

The program is compiled in C23 mode to keep the chapter's examples on one current baseline. Its purpose is to show a version-macro probe; it does not turn C17 into a new feature set.

### 4. Formal boundary

- Use **ISO/IEC 9899:2018** when publication precision matters.
- “C17” and “C18” are not two separate standards.
- Do not claim that nothing changed. Corrections and clarifications matter to correct interpretation.
- For a claim about a specific defect, consult the relevant WG14 Defect Report or change record. Do not infer the details from an edition summary.
- Do not assume every compiler implements every correction without bugs.

### 5. Practical consequence

If a project needs a baseline that incorporates C11 corrections, select a supported C17/C18 mode and document the compiler version. When a bug appears, determine whether it comes from the code, a standards defect, or an implementation bug. Do not describe all such issues as “C17 changes.”

### 6. Retrieval question

Why do C17 and C18 refer to the same ISO/IEC 9899:2018 publication? What was the edition's main focus, and why do corrections matter even when an edition is not a major feature revision?

**Retrieval item ID:** `C23-P00-CH02-S07-RET-01`  
**Candidate misconception ID:** `MIS-P00-CH02-S07-01`

### What C17/C18 changed—and what it did not

C17/C18 is best understood as a corrected publication of the C11 standard, not as a new feature generation comparable to C99, C11, or C23.

| Question | Accurate answer |
|---|---|
| What is the published document? | ISO/IEC 9899:2018 |
| Why do people say C17? | The revision work and common naming refer to 2017 |
| Why do people say C18? | The ISO publication year was 2018 |
| Did it introduce a broad new feature set? | No; it primarily incorporates defect corrections and clarifications |
| Does `-std=c17` select a different broad language feature set from `-std=c11`? | GCC documents the same corrections for both modes, with a different `__STDC_VERSION__` value |
| Does a C17 label prove that every C11 optional facility is implemented? | No |

### Defect correction is not feature invention

A defect report identifies a problem, ambiguity, or issue in the standard text or its interpretation. The committee's response may clarify how existing wording is understood or lead to corrected text in a later publication. That process is different from adding a new language feature.

A useful mental sequence is:

1. A published edition establishes a normative text.
2. Users and implementers identify a possible defect or ambiguity.
3. The committee considers the issue and records its response.
4. Corrections are incorporated into a later corrected publication or otherwise addressed through the standards process.
5. Implementations update their behavior and documentation over time.

Do not infer from this sequence that every committee response automatically changes every previously published edition in the same way. Record the document and status that support the particular claim.

## 0.2.8 — C23 / ISO/IEC 9899:2024: language, preprocessing, and library changes

**Knowledge-unit ID:** `C23-P00-CH02-S08`  
**Importance:** Critical  
**Memory layers:** Atomic · Conceptual · Procedural · Relationship · Engineering Judgment

### 1. Core idea

C23 is the ISO C revision published in 2024 as ISO/IEC 9899:2024. It introduces changes across the core language, preprocessing, types, attributes, and library.

### 2. Mental model

C23 is a published standard edition, not merely “the next C proposal.” WG14 drafts help the public study the text and its development history, but the normative publication is ISO/IEC 9899:2024.

Organize C23 changes into four categories:

1. **Core language and types** — declaration and expression forms, and available types.
2. **Preprocessor** — how a translation unit is formed.
3. **Attributes and diagnostics** — standardized metadata and diagnostic facilities.
4. **Library** — added headers and APIs or revised facilities.

### 3. Technical mechanism

The following is a useful orientation map of well-known C23 changes. It is **not exhaustive** and does not replace clause-level review.

| Area | Example C23 change | What to recognize |
|---|---|---|
| Boolean | `bool`, `true`, and `false` become keywords; `_Bool` remains part of the language | Distinguish keywords from historical header/macro behavior |
| Null pointer | `nullptr` and the related `nullptr_t` type | A more explicit null pointer constant |
| Integer types | `_BitInt(N)` and the bit-precise integer family | Integers with a specified bit width |
| Declarations/types | `typeof`, `typeof_unqual`, `auto` for type inference in specified contexts, and `constexpr` | Changes to declaration and expression rules |
| Literals | Binary integer constants `0b...` and digit separator `'` | Additional ways to write constants |
| Attributes | Standard attributes using `[[...]]` | Standard attribute syntax, distinct from vendor attributes |
| Preprocessor | `#elifdef`, `#elifndef`, `#warning`, and `#embed` | Control and data inclusion during preprocessing |
| Library | `<stdbit.h>`, `<stdckdint.h>`, and other API changes | Bit utilities and checked integer arithmetic |
| Language consistency | Removal or tightening of some old forms, including implicit `int` and old-style function definitions | Legacy code may need updates |

A compact C23 example:

```c
#include <stdbool.h>
#include <stdio.h>
#include <stddef.h>

int main(void)
{
    bool ready = true;
    int *p = nullptr;

    printf("ready=%d, null=%d\n", ready, p == nullptr);
    return 0;
}
```

In C23, `bool`, `true`, and `false` are keywords. `<stdbool.h>` remains for compatibility, but it no longer serves the same role it did before C23. Availability of C23 features still depends on the compiler and library versions.

Preprocessor example:

```c
#if __STDC_VERSION__ >= 202000L
#  warning "This implementation advertises a C2x/C23-era language mode"
#endif
```

This example illustrates a preprocessor diagnostic and a standard-version macro. A compiler's reported macro value during a transition must not be used by itself as proof of complete C23 support.

### C23-compatible lab: Boolean keywords

```c
#include <stdio.h>

int main(void)
{
    bool enabled = true;
    static_assert(sizeof(bool) >= 1, "bool must occupy storage");
    printf("enabled = %d\n", enabled);
    return 0;
}
```

Compile: `gcc -std=c23 -pedantic-errors -Wall -Wextra -Werror c23_bool.c -o c23_bool`.

This example demonstrates C23 keyword spellings supported by the tested GCC release. Check the compiler status page before relying on any other C23 feature.

### 4. Formal boundary

- Published edition: **ISO/IEC 9899:2024**; common community name: **C23**.
- WG14 lists N3220 as a draft related to the C23 edition, but the WG14 project page identifies it as a similar draft and lists it as an early C2y draft in the current project listing. For clause-level certainty, consult ISO/IEC 9899:2024.
- Compiler support is not the same as library support. GCC distinguishes language-dialect support from facilities supplied by the C library and platform.
- Do not assume that every C23 feature is available in older compilers, every embedded target, or every library.
- Do not assume that `__STDC_VERSION__` alone proves support for every feature.
- Verify the status and requirements of specific features—especially optional or conditionally supported features and library changes—against the relevant C23 clauses and annexes before making portability claims.

### 5. Practical consequence

For a new project:

- Set `-std=c23` or the equivalent option for the selected compiler explicitly.
- Record both the compiler version and the C library version, not just the compiler name.
- Add feature probes for the features the project actually uses.
- Run strict/pedantic builds and test on the actual target.
- Distinguish “the compiler accepts the syntax,” “the library provides the API,” and “the program meets the standard's requirements.”

For projects that must support multiple toolchains, consider C17 as a baseline if C23 support is not yet adequate, or document the exact C23 subset in use.

### 6. Retrieval question

Name four groups of C23 changes and give one example from each. Why must ISO/IEC 9899:2024, WG14 drafts, compiler support, and library support be recorded as separate facts?

**Retrieval item ID:** `C23-P00-CH02-S08-RET-01`  
**Candidate misconception ID:** `MIS-P00-CH02-S08-01`

### Removed legacy forms are part of a migration plan

C23 does not only add syntax. It also removes or changes legacy forms. In particular, old-style function definitions using identifier lists and unprototyped function declarations are no longer part of the C23 language model in the way they were historically used.

Migration should therefore include:

1. Search for old-style function definitions.
2. Search for declarations with empty parameter lists whose old meaning depended on an unspecified parameter list.
3. Replace legacy forms with explicit prototypes and definitions.
4. Compile in the intended C23 mode with diagnostics enabled.
5. Review function-pointer declarations and callback interfaces.
6. Check generated code and public headers, not only application source.
7. Verify compatibility with older compilers if the project supports older standards.

## 0.2.9 — Published standards, WG14 drafts, Technical Reports, Technical Specifications, and proposals

**Knowledge-unit ID:** `C23-P00-CH02-S09`  
**Importance:** Critical  
**Memory layers:** Atomic · Conceptual · Procedural · Engineering Judgment

### 1. Core idea

WG14 and ISO documents have different statuses and purposes. A proposal or draft must not be treated as though it were already a requirement in a published C standard.

### 2. Mental model

Check the **status label before reading the content**:

- **International Standard (IS):** a published standards document.
- **Working draft:** a working text under development or previously used during development; it can change.
- **Technical Report (TR):** a technical document that reports study results or guidance/extensions; it is not automatically part of the main ISO C standard.
- **Technical Specification (TS):** a technical specification published through the TS process. Its status and relationship to the main standard must be determined from the document itself.
- **Proposal:** a suggested change. It does not become a rule merely because it was discussed or accepted for consideration.

The practical lesson is simple: do not judge a document only by how official it looks. Check its publication label and process status, just as you would check a software release version before relying on an API.

### 3. Technical mechanism

| Document type | Practical purpose | Can it automatically be cited as a rule in the main ISO C standard? |
|---|---|---|
| ISO/IEC 9899:2024 | Published C language standard | Yes, within the scope of that edition |
| WG14 working draft (e.g., N1570 or N3220) | Working text that helps track standard development | No; verify its status and consistency with the final publication |
| Technical Report (TR) | Technical report on a particular topic; may inform work or provide a reference | No, not automatically |
| Technical Specification (TS) | Technical specification for a particular area | Not automatically part of ISO/IEC 9899; check whether it was later adopted |
| WG14 proposal/paper | Proposed change or discussion | No |
| Defect report / change and clarification request | Request for correction or interpretation and the WG14 response process | Check its status and response; do not assume every request changes the standard |

Examples of real document relationships:

- WG14 records ISO/IEC 9899:2024 as the C23 publication and N3220 as a related draft.
- WG14 lists **TR 18037** for Embedded C as a Technical Report.
- WG14 lists **TS 18661** as a Technical Specification for floating-point extensions. Some of its material was later adopted into C23. The status of a TS before adoption differs from the status of material that ultimately enters the main standard.
- WG14 lists **TS 17961** for secure coding rules. Its existence does not mean that every provision automatically becomes an ISO C language requirement.

### C23-compatible lab: mode evidence is not document classification

```c
#include <stdio.h>

int main(void)
{
#ifdef __STDC_VERSION__
    printf("selected mode macro = %ld\n", (long)__STDC_VERSION__);
#endif
    puts("A compiler macro cannot classify a WG14 paper.");
    return 0;
}
```

Compile: `gcc -std=c23 -pedantic-errors -Wall -Wextra -Werror document_status.c -o document_status`.

The code reports implementation mode evidence only. Document status must be checked from the document's issuing body, title, revision, and publication process.

### 4. Formal boundary

- The presence of “WG14” on a cover does not give every document the same normative force.
- An `Nxxxx` document number identifies a WG14 paper/document. The number itself does not mean “published standard.”
- A final or near-final draft must still be distinguished from the final ISO publication.
- TRs and TSs have different purposes and publication processes. Do not treat them as interchangeable or assume that either automatically becomes part of ISO/IEC 9899.
- A proposal may be accepted, rejected, revised, deferred, or incorporated into another document. Check the decision and resulting document.
- When citing a normative rule, state the standard edition and clause. When citing a draft, state the document number, revision/date, and status.

### 5. Practical consequence

Before adding a standards claim to documentation, a code review, or teaching material, make four checks:

1. What kind of document is it?
2. Is its status final/published, or is it still a draft/proposal?
3. Has its text been adopted into ISO/IEC 9899, and in which edition?
4. Does the cited clause actually support the claim?

If uncertain, write “WG14 proposal” or “WG14 draft,” not “C23 requires.”

### 6. Retrieval question

Given a WG14 Nxxxx paper, how would you determine whether it contains a current ISO C rule, a draft, a TS/TR, or a proposal? Why is the document number alone insufficient?

**Retrieval item ID:** `C23-P00-CH02-S09-RET-01`  
**Candidate misconception ID:** `MIS-P00-CH02-S09-01`

### Document-status ladder

The word “official” is too vague for standards work. Identify the document type and its status before using it as evidence.

| Document class | Typical role | Can it alone be cited as the published C language standard? |
|---|---|---|
| International Standard (IS) | Published normative standard approved through the ISO process | Yes, when the correct edition is identified |
| Committee draft (CD) | Draft circulated for committee or formal comment/ballot stages | No; it is a draft |
| Draft International Standard (DIS) | Draft at an international approval stage | No; publication is not yet complete |
| Final Draft International Standard (FDIS) | Final approval draft before publication | No; it is not the published IS |
| WG14 working draft | Working text maintained during development | No; it may change |
| Proposal paper | Suggests a feature, wording, or change | No; proposal status does not establish adoption |
| Technical Report (TR) | Technical report on a defined topic, often informative or supplemental | Not as the main language standard; check its stated status and scope |
| Technical Specification (TS) | A specification published through a technical specification process | Not automatically part of ISO/IEC 9899; check its scope and relationship |
| Defect/change record | Documents a reported issue and committee response | It is evidence about the issue, not a substitute for identifying the applicable edition |

A document number is an identifier, not a maturity level. A numbered WG14 paper can be a proposal, a draft, a response, or another document class. Read its title, status, date, and committee context.

### Standards citation record template

For each important claim, maintain a record with these fields:

| Field | Required content |
|---|---|
| Claim ID | Stable identifier in the project or chapter |
| Claim | Exact proposition being asserted |
| Standard edition | For example, ISO/IEC 9899:2024 |
| Clause | Exact clause/subclause after direct verification |
| Source class | IS, draft, TR, TS, proposal, compiler documentation, or platform documentation |
| Normative status | Normative, informative, explanatory, or implementation-specific |
| Behavior category | Defined, implementation-defined, unspecified, undefined, optional/conditional, or extension |
| Version difference | Relevant difference from earlier C editions |
| Verification date | Date the source was checked |
| Reviewer note | Any limitation, unresolved ambiguity, or target-specific caveat |

If the clause has not been checked directly, write **to be verified with an authoritative source**. Never invent a clause number to make a reference look complete.

### Retrieval ladder

- **Free recall:** Name the difference between an IS, draft, TR, TS, and proposal.
- **Precision recall:** Explain why a numbered WG14 paper is not automatically normative.
- **Classification:** Identify the source class for N3220 and a compiler status page.
- **Error diagnosis:** Correct a statement that quotes a proposal as a C23 requirement.
- **Transfer retrieval:** Build a source record for one feature used by a real project.

## 0.2.10 — C2y/C29 as future work, not part of C23

**Knowledge-unit ID:** `C23-P00-CH02-S10`  
**Importance:** Core  
**Memory layers:** Atomic · Conceptual · Relationship · Engineering Judgment

### 1. Core idea

C2y is the current WG14 working label for the next revision after C23. “C29” is an informal publication-horizon estimate, not a published standard identifier. Future proposals and drafts do not change the published C23 edition unless the relevant standards process adopts those changes.

### 2. Mental model

C23 is a published release; C2y is the next line of work. A feature that appears in a future-generation draft does not become a C23 feature retroactively.

Use the software-version analogy carefully. Formal standards development is not identical to a vendor release cycle, but distinguishing a final version from a development version remains useful.

### 3. Technical mechanism

- WG14 records C23 as ISO/IEC 9899:2024.
- WG14 lists **C2y** as the next revision under development and shows no published C2y International Standard in the status snapshot checked on November 5, 2026. The project page identifies N3886, dated May 24, 2026, as a C2y draft.
- A compiler may provide an experimental mode, such as GCC's `-std=c2y` option. That support is experimental and may be incomplete according to the compiler documentation; it does not prove that a feature belongs to C23.
- Proposals can change or fail to be adopted. Programmers testing future features should isolate experimental code and state compiler requirements explicitly.

Example project policy:

```text
Production baseline : C23 (ISO/IEC 9899:2024)
Experiment          : C2y draft features, prototype/branch only
Portability claims  : none for draft features until final status is verified
```

### C23-compatible lab: keep the production baseline explicit

```c
#include <stdio.h>

int main(void)
{
    puts("Production language baseline: C23");
    puts("Future proposals remain isolated experiments");
    return 0;
}
```

Compile: `gcc -std=c23 -pedantic-errors -Wall -Wextra -Werror baseline_policy.c -o baseline_policy`.

This example intentionally uses only ordinary C23-compatible facilities. It does not use draft-only syntax, which is the point: a project can state a future-work policy without making its production baseline depend on a future proposal.

### 4. Formal boundary

- **C23** has been published; **C2y** is subsequent work according to the cited WG14 status.
- **C29** is an estimated/informal label that may appear in community discussions about a later cycle. Do not present it as a published standard number or a confirmed final date without an official source.
- `-std=c2y` is a compiler option, not an ISO document.
- Features implemented before finalization may change, be removed, or differ from their final form.
- Because the status of future work changes over time, record the date on which the source was checked.

### 5. Practical consequence

Do not include draft features in a C23 portability baseline without labeling them. If you experiment:

- keep the code separate from production code;
- document the compiler, version, and flags;
- provide a fallback or feature guard where practical; and
- review the code again when a new draft or final standard is published.

### 6. Retrieval question

Why does code accepted by a compiler with `-std=c2y` not automatically qualify as C23? What must happen before a draft feature can become a production contract?

**Retrieval item ID:** `C23-P00-CH02-S10-RET-01`  
**Candidate misconception ID:** `MIS-P00-CH02-S10-01`

### Current status snapshot and date discipline

The WG14 project-status page checked on November 5, 2026 lists **C2y** as the next revision of ISO/IEC 9899 and identifies draft N3886 dated May 24, 2026. It does not list a published C2y International Standard. The schedule is a plan, not a guarantee of final publication on a particular date.

The label **C2y** is the current working name for the next revision cycle in the cited WG14 materials. **C2z** is not established by those sources as a published standard or a confirmed official successor label. Treat it as informal speculation unless an authoritative WG14 document establishes otherwise. Similarly, “C29” may appear as an informal estimate tied to a possible publication horizon; it is not the identifier of a currently published standard.

### What `-std=c2y` actually tells you

A command such as `gcc -std=c2y` asks GCC to compile in its experimental C2y mode. GCC's status documentation describes support as experimental and incomplete. The command tells you which compiler mode was requested; it does not tell you that the source is portable, that the proposal is final, or that another compiler implements the same behavior.

Use separate labels in source code, build scripts, and release notes:

- **C23 baseline:** portable claims are measured against ISO/IEC 9899:2024.
- **C2y experiment:** code is explicitly experimental and tied to a dated draft and compiler release.
- **Compiler extension:** behavior is specific to an implementation or its extension mode.
- **Platform API:** behavior is governed by an operating-system, hardware, or vendor contract.

### Safe experimental workflow

1. Keep draft-feature experiments in a separate branch or isolated module.
2. Record the proposal identifier and the draft revision in which the feature appears.
3. Record the compiler name, version, target triple, and exact flags.
4. Compile with strict diagnostics where possible.
5. Add tests that exercise the intended semantics, not only syntax acceptance.
6. Avoid exposing draft-only declarations in stable public headers.
7. Provide a fallback when the project needs to support C23-only compilers.
8. Re-check the proposal after each WG14 revision.
9. Re-run tests when the compiler changes its experimental implementation.
10. Remove or revise the experiment if the proposal changes or is not adopted.
11. When the next standard is published, compare the final text with the draft the project used.
12. Update the project's language baseline only through an explicit compatibility review.

## Misconception Defense Registry

This registry contains **specific misconceptions worth testing**. It does not claim that a particular learner has made any of these errors. Record learner evidence separately after diagnosis. Code samples are conceptual illustrations, not quotations from normative text.

### `MIS-P00-CH02-01` — Treating the first K&R edition as an ISO standard

- **Incorrect belief:** “If it appears in the first K&R book, it is the official C rule that applies today.”
- **Correct explanation:** The first K&R edition (1978) is an influential book describing pre-ANSI C. ANSI/ISO standards were published later and define the formal contract for each edition.
- **Why plausible:** The book is famous, was written by key figures in C's development, and is often cited as a classic reference.
- **Relevant chapter:** `0.2.1`, `0.2.2`
- **Concrete case:** An old K&R function definition with parameter declarations following the parameter list must not automatically be treated as the recommended style or governing rule for C23.
- **Diagnostic question:** Can a 1978 book directly prove that a construct is required or permitted by ISO/IEC 9899:2024? Why or why not?
- **Correction exercise:** Compare a function declaration from an old K&R source with a modern prototype. Label which statements are historical facts and which normative claims require verification.
- **Related misconceptions:** `MIS-P00-CH02-S02-01`, `MIS-P00-CH02-S03-01`

### `MIS-P00-CH02-S01-01` — Treating B, NB, and C as standard-version names

- **Incorrect belief:** “B, NB, C89, and C90 are simply sequential version names for the same standard.”
- **Correct explanation:** B and NB belong to the pre-C development history. C89/C90 are names associated with ANSI/ISO standard publications.
- **Why plausible:** All the names appear on one timeline and are historically related.
- **Relevant chapter:** `0.2.1`
- **Concrete case:** Referring to an “ISO B standard” or an “NB version of C23” confuses language history with standard identity.
- **Diagnostic question:** Which terms name predecessor languages, and which identify published standards?
- **Correction exercise:** Sort `B`, `NB`, `C`, `K&R 1978`, `ANSI X3.159-1989`, and `ISO/IEC 9899:1990` into two groups: language history and standards/documents.

### `MIS-P00-CH02-S03-01` — Treating C89 and C90 as two technically different revisions

- **Incorrect belief:** “C90 added language features beyond C89 because the years are different.”
- **Correct explanation:** ANSI X3.159-1989 was adopted by ISO as ISO/IEC 9899:1990. GCC documentation reports no technical difference between the two publications, although section numbering was adjusted.
- **Why plausible:** The names and years differ, making them look like two language releases.
- **Relevant chapter:** `0.2.3`
- **Concrete case:** Describing `C89 → C90` as two major feature revisions without explaining the ISO adoption is misleading.
- **Diagnostic question:** According to the cited documentation, what changed when the 1989 ANSI document became the 1990 ISO publication?
- **Correction exercise:** Rewrite “C90 introduced feature X after C89” as an accurate historical statement. If feature X is unsupported, remove the claim.
- **Related misconceptions:** `MIS-P00-CH02-01`

### `MIS-P00-CH02-S04-01` — Treating a wide character as identical to a Unicode code point

- **Incorrect belief:** “One `wchar_t` always stores exactly one Unicode character.”
- **Correct explanation:** C wide-character facilities and the representation of `wchar_t` depend on the implementation and locale. Do not assume `wchar_t` is identical to one Unicode scalar value or one grapheme.
- **Why plausible:** “Wide character” is often simplified to mean “Unicode character.”
- **Relevant chapter:** `0.2.4`
- **Concrete case:** A program that assumes `wchar_t text[2]` is always enough for one visible non-ASCII character has no portability basis from the type name alone.
- **Diagnostic question:** Does the C standard guarantee that one `wchar_t` equals one visible Unicode character on every implementation?
- **Correction exercise:** Explain the difference among encoding, code unit, code point, and grapheme cluster. Identify the platform contract to check before choosing a text API.
- **Related misconceptions:** Portability; Types.

### `MIS-P00-CH02-S05-01` — Assuming every C99 feature is always available

- **Incorrect belief:** “If a compiler claims C99 support, every C99 feature is available on every target.”
- **Correct explanation:** Implementations have hosted/freestanding categories, and some features or facilities have specific support requirements. The compiler and target library are also separate components.
- **Why plausible:** The `-std=c99` mode name looks like a switch that enables every capability without conditions.
- **Relevant chapter:** `0.2.5`
- **Concrete case:** Relying on VLAs or complex facilities in an embedded toolchain without checking target support.
- **Diagnostic question:** Besides `-std=c99`, what must be checked before using a feature on a freestanding target?
- **Correction exercise:** Create a table for “language/compiler,” “library,” and “target.” Record evidence of support for one C99 feature on a real toolchain.
- **Related misconceptions:** Portability; Types; Declarations.

### `MIS-P00-CH02-S06-01` — Assuming atomic means the entire program is thread-safe

- **Incorrect belief:** “If a counter is declared as `atomic_int`, all related data read or written by threads is automatically safe.”
- **Correct explanation:** Atomic operations govern the atomic object and those operations according to the selected memory order. Synchronization and data races involving other objects still require separate analysis.
- **Why plausible:** The word “atomic” sounds like a guarantee of overall concurrency safety.
- **Relevant chapter:** `0.2.6`
- **Concrete case:**

  ```c
  atomic_int ready = 0;
  int payload = 0;

  /* Thread A */
  payload = 42;
  atomic_store_explicit(&ready, 1, memory_order_relaxed);

  /* Thread B */
  if (atomic_load_explicit(&ready, memory_order_relaxed))
      use(payload);
  ```

  This example does **not** establish synchronization for publishing `payload` merely by using `memory_order_relaxed`. Do not use it as a safe inter-thread communication pattern.
- **Diagnostic question:** What guarantee does atomicity provide for `ready`, and what guarantee does it not provide for `payload`?
- **Correction exercise:** Explain an appropriate release/acquire design, then verify the rules and examples in the concurrency chapter before claiming that the program is free of data races.
- **Related misconceptions:** Concurrency; Behavior.

### `MIS-P00-CH02-S07-01` — Treating C17 and C18 as separate standards

- **Incorrect belief:** “C17 and C18 are two different revisions.”
- **Correct explanation:** Both names refer to ISO/IEC 9899:2018 in community usage; WG14 records the publication in 2018.
- **Why plausible:** The community uses two labels, and the target year and publication year differ.
- **Relevant chapter:** `0.2.7`
- **Concrete case:** A project document that lists “C17” and “C18” as two independently selectable ISO editions is misleading unless it defines a specific toolchain convention.
- **Diagnostic question:** What is the formal ISO publication identifier shared by C17 and C18?
- **Correction exercise:** Rewrite a project baseline statement using ISO/IEC 9899:2018 and explain the community labels.

### `MIS-P00-CH02-S08-01` — Treating compiler acceptance as proof of C23 conformance

- **Incorrect belief:** “The compiler accepts this C23-looking syntax, so the program is fully C23-conforming.”
- **Correct explanation:** Acceptance proves only that the selected compiler, flags, library, and target accepted the program. It does not prove full standard conformance or portability to other implementations.
- **Why plausible:** A successful build is visible and easy to mistake for a complete conformance test.
- **Relevant chapter:** `0.2.8`
- **Concrete case:** A compiler accepts `nullptr` in a transitional mode, but the target library or another required C23 feature is missing.
- **Diagnostic question:** What exactly does one successful compilation establish, and what does it leave unproven?
- **Correction exercise:** Record compiler version, flags, target, library, feature probes, and the relevant normative source. Separate observed support from the conformance claim.
- **Related misconceptions:** Portability; Standards evidence.

### `MIS-P00-CH02-S09-01` — Treating every WG14 paper as a published standard

- **Incorrect belief:** “Any document with a WG14 number is an official C standard requirement.”
- **Correct explanation:** WG14 papers include drafts, proposals, defect reports, and other document types. Their status and adoption history must be checked.
- **Why plausible:** Numbered committee documents look formal and authoritative.
- **Relevant chapter:** `0.2.9`
- **Concrete case:** Citing a proposal as “C23 requires” without confirming that the proposal was adopted into ISO/IEC 9899:2024.
- **Diagnostic question:** What evidence proves that a WG14 proposal became part of a published standard?
- **Correction exercise:** Classify one WG14 document by type, date, status, and relationship to the published standard.
- **Related misconceptions:** Standards literacy; Normative citation.

### `MIS-P00-CH02-S10-01` — Treating C2y features as part of C23

- **Incorrect belief:** “If a compiler implements a feature in `-std=c2y` mode, that feature is already part of C23.”
- **Correct explanation:** C2y is future work after C23. Experimental compiler support does not amend a published ISO edition.
- **Why plausible:** The compiler accepts the feature, and the draft may look close to a final specification.
- **Relevant chapter:** `0.2.10`
- **Concrete case:** A product claims “C23 support” because it uses a feature available only in an experimental C2y mode.
- **Diagnostic question:** What published document establishes C23, and what is the status of C2y in the cited WG14 project record?
- **Correction exercise:** Rewrite the product claim to distinguish published C23 support from experimental C2y support.
- **Related misconceptions:** Standards status; Compiler acceptance.

### Six-step repair loop (required)

Use this sequence whenever a misconception appears:

1. **Name the claim.** Write the incorrect statement exactly as it was made.
2. **Classify the confusion.** Identify whether it concerns history, document status, language semantics, implementation support, or portability.
3. **Find the authoritative boundary.** Identify the published edition, relevant clause, WG14 record, or compiler documentation needed to evaluate the claim.
4. **State the corrected model.** Explain the distinction in one or two precise sentences.
5. **Apply it to a new case.** Use a different example to show that the correction transfers beyond the original question.
6. **Schedule retrieval.** Re-test after a delay and record the evidence; do not mark the misconception resolved merely because the explanation was read.

## Pitfall box — the trap that most often undermines portability claims

> **Do not infer the language standard from one compiler result.** A successful compilation proves only that the selected compiler, flags, library, and target accepted the program. It does not prove ISO C conformance, library availability on another target, or identical behavior across all implementations.

Before making a portability claim, record at least the language mode, compiler/version, target, library/runtime, diagnostics, and the normative source supporting the feature. Distinguish implementation extensions from standard features.

### Chapter summary and final checks

C grew from early systems-language work into a standardized language with successive published editions and corrections. The important skill is not memorizing labels alone; it is identifying which document and implementation contract support a claim.

| Milestone | Relationship to the next step |
|---|---|
| B / NB / early C | Historical development before formal C standardization |
| K&R first edition (1978) | Influential description of pre-ANSI C |
| ANSI X3.159-1989 / C89 | First ANSI C standard |
| ISO/IEC 9899:1990 / C90 | ISO adoption of the ANSI standard |
| C95 | Amendment 1 to C90 |
| ISO/IEC 9899:1999 / C99 | Major language and library revision |
| ISO/IEC 9899:2011 / C11 | Atomics, threads, alignment, and related facilities |
| ISO/IEC 9899:2018 / C17/C18 | Corrected publication of C11 |
| ISO/IEC 9899:2024 / C23 | Published fifth edition of the C standard |
| C2y | Next revision under development; not a published C standard |

- Identify the edition before asserting a rule.
- Verify the document type before citing it.
- Check the exact clause before quoting it.

- Pin the language flags.
