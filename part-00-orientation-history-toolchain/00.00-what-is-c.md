# 0.1.1 --- C as a procedural, structured, system-oriented programming language

**Knowledge-unit ID:** `C23-P00-CH01-S01`\
**Retrieval item ID:** `C23-P00-CH01-S01-RET-01`\
**Importance:** Core

## 1. Core idea

**C is a general-purpose, compiled programming language in which
programmers commonly organize work as functions and explicit control
flow, while directly expressing operations on typed objects and their
values.**

"Procedural," "structured," and "system-oriented" describe useful
characteristics of C; they are not three special language modes that a
program switches on.

## 2. Mental model --- instructions, decisions, and state

Imagine a small workshop:

-   **State** is the material currently on the workbench.
-   **Statements** are the operations performed on that material.
-   **Selection** (`if`, `switch`) chooses a path.
-   **Iteration** (`for`, `while`, `do`) repeats a process.
-   **Functions** package a task behind a name and a
    parameter/return-value interface.

This model helps explain procedural programming: a program is often
understood as a sequence of operations that transform state.

**Limit of the model:** C is not merely a list of instructions executed
exactly as written from top to bottom. Expressions have formal
evaluation and sequencing rules; compilers may transform code while
preserving the behavior required by the C abstract machine. Also, C
permits `goto`, recursion, callbacks, function pointers, and other
structures that do not fit a simplistic "one straight line" picture.

### What the three descriptions mean

-   **Procedural:** A common design style is to divide work into
    functions that perform operations, accept inputs, and return results
    or modify objects through pointers.
-   **Structured:** C provides blocks and control-flow constructs such
    as `if`, `switch`, loops, and function calls. These make program
    flow explicit and composable. C also retains `goto`; "structured"
    does not mean that every possible jump is forbidden.
-   **System-oriented:** C gives programmers explicit control over
    object types, storage duration, data representation constraints,
    pointer operations, and interaction with implementation- or
    platform-provided facilities. This is useful near operating systems
    and hardware, but it does not mean that every hardware detail is
    portable ISO C.

## 3. Technical mechanism --- functions, blocks, and state changes

Consider this complete program:

``` c
#include <stdio.h>

static int square(int value)
{
    return value * value;
}

int main(void)
{
    const int input = 7;
    const int result = square(input);

    if (result > 40) {
        puts("The result is greater than 40.");
    } else {
        puts("The result is 40 or less.");
    }

    printf("%d squared is %d\n", input, result);
    return 0;
}
```

Build and run it:

``` sh
gcc -std=c23 -Wall -Wextra -pedantic square.c -o square
./square
```

Expected output:

``` text
The result is greater than 40.
7 squared is 49
```

Read the program as a small system:

1.  `main` is the entry function for this hosted example.
2.  `input` and `result` are objects with declared types and values.
3.  `square` is a function with an `int` parameter and an `int` result.
4.  The `if` statement selects one block.
5.  `printf` and `puts` use the hosted C standard I/O library.

The `static` on `square` gives the function name internal linkage in
this translation unit. It is not what makes the function "procedural";
the function definition and call are the relevant organizational
features.

A function can also communicate through pointers. That is powerful, but
it introduces obligations about valid objects, lifetimes, and bounds.
Those topics are developed in later chapters.

## 4. Formal boundary --- what is guaranteed and what is not

The words *procedural*, *structured*, and *system-oriented* are
explanatory descriptions, not normative classifications in ISO C. The
standard specifies syntax, constraints, and semantics; it does not
require a particular software architecture.

  -----------------------------------------------------------------------
  Category                            Boundary for this topic
  ----------------------------------- -----------------------------------
  **Defined**                         The standard specifies the meaning
                                      of valid function
                                      definitions/calls, blocks,
                                      selection statements, and iteration
                                      statements. The example above uses
                                      ordinary defined behavior in a
                                      hosted implementation.

  **Implementation-defined**          Some properties relevant to
                                      low-level programming---such as
                                      object representations, alignment
                                      support, and characteristics of
                                      integer types---depend on
                                      documented implementation choices.
                                      Do not infer them from the word
                                      "system-oriented."

  **Unspecified**                     Where the standard permits multiple
                                      possibilities without requiring the
                                      implementation to document which
                                      one it chooses, code must not rely
                                      on a particular choice. For
                                      example, the order of evaluation of
                                      function arguments is unspecified;
                                      do not use it to coordinate side
                                      effects.

  **Undefined**                       A program that violates applicable
                                      semantic requirements can reach
                                      undefined behavior. For example,
                                      dereferencing a null pointer is not
                                      made safe merely because C exposes
                                      pointers.

  **Extension**                       A compiler may accept additional
                                      syntax or built-ins outside the
                                      selected ISO C dialect. Such
                                      acceptance is not automatically
                                      portable C23.

  **Optional**                        Some standard facilities are
                                      conditional features and are not
                                      required in every implementation.
                                      Optional support does not make the
                                      entire C language optional.

  **Historical**                      Older C materials may describe
                                      older declaration rules or compiler
                                      practices. A historical convention
                                      is not a C23 guarantee.
  -----------------------------------------------------------------------

**Standards map:** ISO/IEC 9899:2024 (C23), Clause 5.1.1.2 (translation
phases), Clause 6.8 (statements and blocks), and Clause 6.9.1 (function
definitions). The terminology for implementation-defined, undefined, and
unspecified behavior is in Clause 3.5. The final published standard is
the authority; the publicly available WG14 N3220 text is a useful
standards text for checking the cited wording.

## 5. Practical consequence

When writing C:

-   Give each function a clear responsibility and a documented
    input/output contract.
-   Use blocks and control-flow statements to make decisions and
    repetition visible.
-   Treat every object as having a type and a lifetime; do not assume
    that a variable is simply "a box somewhere."
-   Make pointer validity and array bounds explicit when a function
    receives memory through a pointer.
-   Do not assume that a compiler's acceptance proves that code is
    strictly conforming C23.
-   Separate ISO C facilities from operating-system APIs, hardware
    registers, and compiler extensions.

A good first habit is to ask: **What object is being read or modified,
by which statement, and under what lifetime and type rules?**

## 6. Retrieval question

Without looking back: explain in one sentence what "procedural,"
"structured," and "system-oriented" mean in C. Then identify one thing
the labels do **not** guarantee about a program or its target machine.

# 0.1.2 --- What C is used for

**Knowledge-unit ID:** `C23-P00-CH01-S02`\
**Retrieval item ID:** `C23-P00-CH01-S02-RET-01`\
**Importance:** Core

## 1. Core idea

**C is used where its combination of explicit data representation,
predictable language rules, implementation control, and broad toolchain
availability is useful---but the final choice always depends on the
platform, interfaces, safety needs, and project constraints.**

C is not restricted to operating systems, and it is not automatically
the best choice for every low-level or high-performance task.

## 2. Mental model --- a portable core with platform-specific adapters

Think of a C program as having two broad layers:

-   **C-language layer:** types, expressions, functions, objects,
    control flow, and standard-library facilities.
-   **Platform layer:** operating-system calls, device registers,
    interrupt mechanisms, network sockets, graphics APIs, and other
    external interfaces.

The C layer can often be reused across platforms. The platform layer
connects the program to a particular operating system, processor, board,
or runtime.

**Limit of the model:** The boundary is not always a clean wall. The C
implementation, ABI, compiler options, startup code, linker, and
platform headers can affect how a program is built and integrated.
"Written in C" does not mean "runs unchanged everywhere."

### Example: processing a bounded byte buffer

This example is ISO C code. It counts bytes equal to a chosen value in a
buffer. It does not open a network socket or read a device; it
demonstrates the kind of byte-level operation that can sit inside a
larger networking, storage, or embedded component.

``` c
#include <stddef.h>
#include <stdio.h>

static size_t count_byte(const unsigned char *data,
                         size_t length,
                         unsigned char target)
{
    size_t count = 0;

    for (size_t i = 0; i < length; ++i) {
        if (data[i] == target) {
            ++count;
        }
    }

    return count;
}

int main(void)
{
    const unsigned char packet[] = {
        0x10, 0x20, 0x10, 0x30, 0x10
    };

    const size_t matches =
        count_byte(packet, sizeof packet, 0x10);

    printf("matching bytes: %zu\n", matches);
    return 0;
}
```

Build and run:

``` sh
gcc -std=c23 -Wall -Wextra -pedantic byte_count.c -o byte_count
./byte_count
```

Expected output:

``` text
matching bytes: 3
```

Mechanism:

-   `unsigned char` is suitable for inspecting object bytes.
-   `size_t` represents object sizes and array indexing quantities.
-   The caller supplies both a pointer and a length; the function does
    not guess the buffer size.
-   The loop only accesses indices from `0` through `length - 1` when
    `length` is nonzero.
-   The caller remains responsible for ensuring that `data` points to at
    least `length` readable elements. Passing an invalid pointer or an
    incorrect length can violate the function's contract.

This is a useful pattern in parsers and binary-data processing. It is
not, by itself, a complete packet parser or a complete security
boundary.
